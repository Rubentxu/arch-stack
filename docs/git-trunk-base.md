# Trunk-Based Workflow — `archctl`

> Contrato de branching para todas las sesiones que tocan este
> repo. Heredado del `git-contract.md` de OpenCode y acordado con
> el usuario: el trabajo se hace en branches, los merges a
> `main` son por commit fast-forward o squash, y los commits
> atómicos describen unidades de trabajo, no estados intermedios.

## Reglas

### 1. Branch naming

| Prefijo | Uso | Merge target |
|---|---|---|
| `feat/<scope>` | Cambio sustantivo (feature, refactor, M-cycle, ADR block) | `main` |
| `fix/<scope>` | Bugfix aislado | `main` |
| `docs/<scope>` | Solo documentación, sin código | `main` |
| `chore/<scope>` | Tooling, deps, gitignore, sin cambio funcional | `main` |
| `release/<version>` | Preparación de release tag | `main` |

`main` está protegido: trabajo directo solo para typoes en docs
o cherry-picks verificados. Para todo lo demás, branch.

El `<scope>` es kebab-case y describe el área, no la fecha.
Ejemplos en este repo: `feat/m5-gix-identity`, `feat/scope-gates`,
`docs/post-b2-b3`.

### 2. Atomic commits

Un commit es una unidad lógica mínima. No se commitean:

- Estados intermedios de un refactor (renames + re-namespace en el
  mismo commit que la lógica nueva).
- Mezclas de `feat:` con `docs:` o `chore:`. Si un commit cambia
  código y docs, el mensaje debe reflejar solo el código (la
  doc es follow-up en su propio commit con `docs(...)`).
- `wip` / `tmp` / `untitled` como subject — usar `chore(<scope>):
  WIP <descripción>` solo en branches personales que se descartan.

### 3. Conventional commits (enforced por hook)

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `type` ∈ {`feat`, `fix`, `docs`, `chore`, `refactor`, `test`,
  `perf`, `build`, `ci`, `style`}.
- `(scope)` es opcional y kebab-case (e.g. `(scope-gates)`,
  `(evidence)`, `(adr-016)`).
- `subject` ≤ 72 chars, sin punto final, en imperativo
  ("add gate" no "added gate").
- `body` libre pero recomendado: qué y por qué.
- `footer` para `BREAKING CHANGE: <descripción>` y/o
  `Refs: <token>`.

### 4. Anti-AI-attribution (enforced por hook)

Prohibido en el subject, body o footer:

- `Co-Authored-By: <algo> AI`, `Co-Authored-By: <algo>Bot`,
  nombres de modelos (`GPT`, `Claude`, `Copilot`,
  `mini`, `MiniMax`, etc.).
- `Generated by <AI tool>`.
- Cualquier línea que sugiera que la IA escribió el código sin
  intervención humana.

Por convención, el humano decide; la IA ejecuta. Si la IA
contribuyó a la decisión o al código, queda implícito en el
proceso, no en el commit.

### 5. Recovery tags

Para snapshots que representen un punto de retorno estable, usar
el prefijo `snapshot/<nombre-descriptivo>`:

```bash
git tag snapshot/<description> <sha>
```

En este repo se usa para transiciones de fase. Los snapshots
previos nunca se borran aunque queden obsoletos; documentan la
historia del proyecto.

### 6. Trunk sync

Antes de empezar trabajo nuevo desde `main`:

```bash
git fetch origin  # si hay remoto
git checkout main
git rebase origin/main    # o merge si la historia protege rebase
git checkout -b feat/<new-scope>
```

Antes de mergear un `feat/*` a `main`:

```bash
git diff main..feat/<scope> --stat   # verificar scope del diff
git diff main..feat/<scope> --shortstat
cargo test                          # gate obligatorio
```

### 7. State-handoff al cambiar de sesión

Si una sesión tiene que parar (compaction, fin de jornada, error
recurrente), produce:

1. Tag `snapshot/<description>` apuntando al HEAD actual.
2. Doc en `docs/STATE-<YYYY-MM-DD>-<description>.md` con:
   - Resumen ejecutivo (métricas: tests verde, warnings, etc.).
   - Cambios concretos (commit list).
   - Decisiones pendientes.
   - Comandos de recuperación.

Eso es lo que la siguiente sesión lee primero — Engram queda como
backup, pero el tag + doc en disco son lo que el siguiente
agente ve sin consultar memoria externa.

## Hooks instalados

`.git/hooks/commit-msg` valida:

- Subject matches conventional commit regex.
- Subject ≤ 72 chars.
- Body y footer no contienen `<algo>-by-` con modelo de IA ni
  `Generated by`.

El hook es ejecutable y se commitea bajo
`.git-hooks/commit-msg` (ver `Makefile` o `scripts/install-hooks.sh`,
si existen) — el estándar `core.hooksPath` permite centralizar.

## Failure modes

| Condición | Acción |
|---|---|
| `main` recibió commits directos (no via PR/merge) | Revertir con `git reset --soft HEAD~1` y aplicar vía PR. |
| Hook falla y bloqueó commit legítimo | `git commit --no-verify` solo si el humano verifica que es falso positivo — no usar en agente. |
| Tag de snapshot borrado por accidente | `git tag snapshot/<name> <sha>` lo restaura; los observadores externos (Engram, ROADMAP) lo recuperan. |
| Re-sync necesario después de trabajar offline | `git fetch` + `git rebase` (no merge) sobre `main`, push con `--force-with-lease`. |
